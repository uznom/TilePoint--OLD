## 2026-07-18 - Vite Environment Variable Interpolation Failure
**Vulnerability:** A hardcoded HMAC secret was exposed. Attempting to fix it introduced a system breakage due to improper Vite environment variable injection.
**Learning:** Vite relies on strict static AST analysis (esbuild define) to inject environment variables at build time. Using optional chaining (`env?.VITE_SECRET`) or TypeScript casting (`(import.meta as any).env`) breaks Vite's parser. This causes the variable to silently compile as `undefined` on the client, resulting in a catastrophic cryptographic mismatch between client and server. Furthermore, client and server fallback logic for secrets must be symmetrical to avoid authentication failures in misconfigured environments.
**Prevention:** Always reference Vite environment variables explicitly (e.g., `import.meta.env.VITE_SECURITY_SECRET`). Ensure any required secret fallback logic behaves identically across client and server runtimes, and add TypeScript definitions (`vite-env.d.ts`) rather than using inline casts.
## 2026-07-19 - Hardcoded HMAC Secrets across Application Stack
**Vulnerability:** A critical HMAC signing secret (`TILEPOINT_SECURE_PERIMETER_HMAC_SECRET_2026`) was hardcoded in both the frontend (`src/lib/crypto.ts`) and backend (`server.js`), allowing potential session token forgery if source code is exposed.
**Learning:** In applications with shared logic or symmetry between client and server (like session signing), removing hardcoded secrets requires careful orchestration. The secret must be provided via environment variables (like `dotenv` for Node and `import.meta.env` for Vite), AND any fallback mechanisms must be identical on both ends. Otherwise, cryptographic mismatches occur.
**Prevention:** Use environment variables for secrets, ensure symmetric fallback logic when defaults are necessary, and add TypeScript definitions for Vite env variables to prevent compilation issues.

## 2026-08-05 - Prevent SQL Injection in AlaSQL Fallback Queries
**Vulnerability:** SQL injection vulnerability existed in `server.js` fallback database lookup methods (like `getSalesWithItemsLookups`, `getInventoryAndBranchStockLookups`, `getInventoryMovementsLookups`, and `getShiftSalesSummaryLookups`) where user input (e.g., `branchId`, `shiftId`, `cashierId`) was concatenated directly into AlaSQL queries using template strings and `+` concatenation.
**Learning:** Even fallback embedded SQL engines like AlaSQL are susceptible to SQL injection when they parse and execute string-based queries directly. In this codebase, AlaSQL fully supports parameterized queries via arrays `alasql(query, [params])`, which is the safer and correct approach.
**Prevention:** Always use parameterized arrays when passing variables to `alasql`, for example: `alasql('SELECT * FROM table WHERE col = ?', [val])` rather than template literals. Avoid string concatenation at all times when constructing query strings that incorporate user-provided filters.
